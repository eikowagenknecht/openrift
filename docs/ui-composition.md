# UI composition

How the web app's page chrome and card-browser surfaces are assembled. Read this before adding a page header, a sticky toolbar, or a new surface that shows a grid of cards.

## Page widths

There are exactly two page widths, both in `PAGE_WIDTH` (`apps/web/src/lib/utils.ts`). A page is `full` (`CONTAINER_WIDTH`: 1280, then 1720 `wide`, 2160 `xwide`, 2560 `xxwide`) when its main content is a card grid, a virtualized list, or a wide table. Every other page is `capped` (`max-w-5xl`). `PageTopBarSticky` takes a required `width` prop of those two values, so a page cannot pick a third by omission, and the content column below the bar uses the matching `PAGE_WIDTH[width]`. `apps/web/src/lib/page-width.test.ts` fails on any new hand-rolled `mx-auto max-w-{2xl…7xl}` page column.

Three things are component widths, not page widths: a long-form text block capped at `max-w-prose` inside a `capped` page (`ProsePage`, `/help/$slug`), a narrow field or dialog (`max-w-sm`, `max-w-md`), and the landing hero. Admin pages carry no page-width wrapper at all. The sidebar layout's content column is their width.

## Top bars and sticky stacking

The app has one global header and one shared page-header primitive. Compose from these; there is no third title row.

- **Global header** (`apps/web/src/components/layout/header.tsx`): the app chrome. `sticky top-0 z-50`, height `h-14`, `border-b backdrop-blur-lg`. It is the only top bar that keeps a bottom border. Every other bar separates by spacing plus blur. Its height is published two ways: the `--header-height` CSS variable (used by `top-(--header-height)` in CSS) and `getHeaderHeight()` (`apps/web/src/lib/header-height.ts`) for JS offset math. They agree: the variable includes the 1px border, and the JS fallback is 57 during SSR.

- **Page top bar** (`apps/web/src/components/layout/page-top-bar.tsx`): the single per-page title row. Compose `PageTopBarBack` / `PageTopBarTitle` / `PageTopBarActions` inside `<PageTopBar>`, hosted in `<PageTopBarSticky>` (which applies `PAGE_TOP_BAR_STICKY`: `sticky top-(--header-height) z-30 px-safe pt-3 pb-2 backdrop-blur-lg sm:pb-3`). Every bar passes the page's `width` so the bar's content aligns with the column below while the blur spans the viewport. Use this for every page-level header: list pages, detail pages, and card-browser surfaces alike. Do not hand-roll a `Heading` plus actions row at the call site. A one-paragraph intro goes in `<PageDescription>` as the first content block below the bar, never inside it, so the sticky bar stays one compact row. Short status chips (role, tournament state, "Simulator") render inline next to the title as a `Badge`. If the page stacks a card-browser toolbar below the title, also measure the bar with `useMeasuredHeight(slotEl)` and publish it via `<PageTopBarHeightContext value={height}>` so the toolbar below can offset correctly. Worked example: `apps/web/src/routes/_app/promos_.$language.lazy.tsx`.

- **Drill-down breadcrumb** (`apps/web/src/components/layout/top-bar-breadcrumb.tsx`): drill-down pages below a tabbed area (groups events/entrants/manage, deck-check) carry a `TopBarBreadcrumbBar`, a sticky `PageTopBar` hosting a `TopBarBreadcrumbTrail` (clickable trail on `sm`+, collapsed to a single back arrow on phones), with the page's own `h1` in content. A detail page whose title lives in the bar itself composes the trail inline with `TopBarBreadcrumbSeparator` plus `PageTopBarTitle` (see `TournamentPageFrame` in `apps/web/src/components/pod-tournaments/tournament-shell.tsx`).

- **Top-bar action buttons** (also in `page-top-bar.tsx`): inside `PageTopBarActions`, use `PageTopBarButton` (secondary labeled action, ghost), `PageTopBarPrimaryButton` (the single filled CTA, at most one per bar), and `PageTopBarIconButton` (icon-only action or overflow-menu trigger, ghost, square). Do not use a raw `<Button>` (or `buttonVariants` on a `<Link>`) here. These wrappers lock `variant` and `size` so every bar shares one height (`h-8`) and the same emphasis ladder. They forward the `render` prop, so render as a link (`render={<Link .../>}`) or as a dialog/menu trigger target (`<DropdownMenuTrigger render={<PageTopBarIconButton />}>`) like `Button`. `PageTopBarBack` follows the same `h-8` sizing. Selects in a top bar use the default `SelectTrigger` size (not `size="sm"`) to match.

- **Card-browser toolbar** (`CardBrowserLayout`, see below): `sticky z-30`, co-planar with the page top bar, offset at `getHeaderHeight() + pageTopBarHeight`. Below it the active-filters strip is `z-15` at the toolbar offset, and grouped grid headers stick below that via `useCardBrowserLayoutOffsets()`. The toolbar shares the bar's `z-30` on purpose: it sits flush under the bar with no top padding, so a focused control's 2px outset ring (`ring-2`, the app-wide focus width) pokes into the bar's `pb` gap. At a lower z the bar's blurred background painted over that strip and clipped the ring. Co-planar lets the ring win the 2px overlap, and since the bar has no bottom border, its edge is covered invisibly in any real overlap.

### Vertical gap rule

The bar's `pb-2 sm:pb-3` sits inside its `backdrop-blur` box, so it is frosted, not clear space. Content whose top edge is flush against the bar lands inside that frosted band, and an outset ring (every `Card` has `ring-1`) gets its top edge eaten. So a content column directly under a `PageTopBarSticky` adds its own `pt-3` to push content, ring included, clear of the band. This is on top of the bar's `pb`, which stays for optical breathing room on phones (8px mobile, 12px desktop, since a borderless title inflates the space below it). Put the `pt-3` on the first content wrapper below the bar. Shells that render a content region (`FriendGroupPageFrame`, the tournament frames in `tournament-detail-frame.tsx`, `pod-tournaments/tournament-shell.tsx`) carry it so their child pages inherit it. The bar's `pb` alone is not the gap; relying on it leaves cards flush.

The card-browser toolbar tier is the exception: it sits flush under the bar on purpose (it is itself a blurred control band, not content with rings), so it adds no top padding. The measured offset chain positions it and the grid lives below it, never flush against the title. A toolbar tier adds its own `pt-3` only when it is the first tier under the global header (no page top bar above, i.e. `pageTopBarHeight === 0`, like `/cards`). `CardBrowserLayout` does this automatically. Any hand-rolled sticky toolbar under a `PageTopBar` (e.g. `/decks`) must follow the same rule.

### Sticky ladder and offset chain

The sticky z-index ladder, top to bottom: header `z-50`, then page top bar `z-30` = toolbar `z-30` (co-planar; DOM order puts the toolbar last, so it wins the 2px focus-ring overlap), then active filters `z-15`, then grid group headers (`z-10` and below). The offset chain is additive and measured, never hardcoded: header height (`getHeaderHeight()` / `--header-height`), plus the measured page-top-bar height (`PageTopBarHeightContext`), plus the measured toolbar height, plus the measured above-grid height. A new surface that uses `CardBrowserLayout` under a `PageTopBar` gets the whole chain for free. Never re-derive these offsets at the call site.

## Card-browser surfaces

Every card-browser surface (`/cards`, `/collections`, `/collections/share`, `/decks/$deckId`, `/promos`) is built from the same shared pieces. Do not re-derive toolbar or above-grid JSX at the call site, and do not re-derive thumbnail wiring inside `renderCard`. Compose from the existing parts. A new surface goes through these five steps:

1. **Filter chrome.** Wrap the surface in `<CardBrowserFilterProvider>` (from `apps/web/src/components/cards/card-browser-filter-scaffold.tsx`) and pass `availableFilters`, `availableLanguages`, `filterCounts`, `setDisplayLabel`, `hiddenSections`, `visibleCustomTagCategories`. Hand `<BrowserToolbar/>` as the layout's `toolbar` (it hosts the compact filter bar, the app's only filter layout) and `<BrowserActiveFilters/>` as `aboveGrid`. Surface-specific toolbar buttons (catalog-mode toggle, owned toggle, etc.) go in `<BrowserToolbar extras={...}/>`. Surface-specific group-by axes (e.g. /promos uses channel / card / year / marker) go in `groupByOptions`.

2. **Layout shell.** Virtualized grids use `<CardViewer>`, or `<BrowserCardViewer>` for selection-store wiring. Non-virtualized grids (like /promos's channel-tree sections) use `<CardBrowserLayout>` directly and provide a custom `gridSlot`. In the non-virtualized case, drive column sizing with `useResponsiveColumns(maxColumns)` and write `autoColumns`, `physicalMax`, `physicalMin` back to `displayStore` so the toolbar's `ColumnControls` reflects the live measurement. Each section then sets `gridTemplateColumns: repeat(${columns}, minmax(0, 1fr))` inline.

3. **Per-cell render.** Inside `renderCard`, use `<CardCell printing ctx display ...>` with named slots: `strip` (one of `OwnedCountStrip` / `CollectionAddStrip` / `DeckAddStrip` / custom), `stripSlot` (`"aboveCard"` or `"topSlot"`), `wrap` (a JSX element like `<DraggableCard ... />` for collections DnD; CardCell injects the composed cell as children via `cloneElement`), `contextMenu` (same JSX-element pattern, e.g. `<DeckCardDetailMenu ... />`), `leftOverlay` (e.g. select-mode checkbox plus ring). The catalog's `<BrowserCardCell>` is the pattern to follow when a cell needs to self-subscribe to live per-cell data: it wraps `CardCell` with `useOwnedCountsForPrintings` and dispatches via the row-actions store.

4. **Table actions.** Pass `table.actionsCell={<XActionsCell ... />}` and a matching `table.actionsColumn` (`"none"` / `"narrow"` / `"wide"`). Per-row data (`printing`, `itemId`) is injected into the actions element via `cloneElement`, so declare them as optional props on the cell component and early-return `null` when `printing` is undefined. Hoist a small per-surface wrapper component that receives the surface's closure data (mutations, lookup maps, etc.) as plain props and renders one of the shared `CatalogTableActions` / `CollectionTableActions` / `StaticCountTableActions` / `DeckTableActions` with the per-row props applied. Same pattern for `table.rowWrapper`: pass a JSX element, and the row node arrives as children via `cloneElement`.

5. **Detail overlay.** Mount `<SelectionDetailOverlays>` as a sibling of the surface's `<SelectionDetailPane>`, with the same `items` / `printingsByCardId` / `showImages` / `onSearchAndClose`. Never mount `SelectionMobileOverlay` or `SelectionDetailModal` directly, and never gate either on `isMobile` at the call site. The overlays component owns that split (drawer on phones, dialog on desktop). Which one shows is the user's `paneDocked` display preference: the pane self-gates on it and the modal stands down while it is on. Three things that bite:
   - **A call-site `isMobile` gate leaves desktop clicks dead.** The public deck share hid this inside a bridge component, so a click selected a card and opened nothing. If a surface wraps the overlay in a bridge (to resolve a pending click, say), the bridge mounts on every viewport and is the sole owner of that effect. Two bridges each running it select the card twice.
   - **A nested browser needs a gate.** The deck editor's `DeckCardBrowser` mounts its own overlay in zone mode, so the editor gates its own to overview mode. Otherwise two copies of the same detail are live at once.
   - **A surface with a pane but no toolbar needs its own toggle.** `DetailPaneToggle` (exported from `filters/options-bar.tsx`) is rendered last in `BrowserToolbar`, after the surface extras, so its position never shifts. The deck overview and the public deck share render no toolbar at all, so `DeckOverview` ends its own view-controls cluster with it.

   Surfaces with add controls also pass `actions`, a `(printing) => ReactNode` that rebuilds the card cell's strip for the shown card, so an overlay never hides the controls it covers. Build it once and use it for both the cell's `strip` and the overlay (`deckStripFor` in `deck-card-browser.tsx`). Where the cell's strip is copy-scoped and the overlay needs a printing-scoped one, write a narrower printing-level one (`CollectionDetailActions`). Read-only surfaces pass nothing.

### Card detail layouts

`CardDetail` renders in two arrangements, picked by its `layout` prop: `"pane"` is the single-column stack (docked pane, mobile drawer, standalone card page), `"modal"` is the two-column dialog. Both compose the same extracted parts (`card-detail-art` / `-stats` / `-text` / `-links`) so a field added to one is never missing from the other. Add to a part, never to one branch. Two sizing traps, both of which shipped as visible jumps: the domain tint belongs to the dialog, not `CardDetail`'s modal root, or the gradient paints inside the dialog's padding and frames itself in a hard edge. And a Suspense fallback must be shaped like the layout it stands in for: the pane's skeleton has an `aspect-card w-full` block, which in an 860px dialog is a ~1150px-tall placeholder that opens the dialog enormous before it snaps down.

### What belongs to the surface

What stays at the surface: the data hook (`useCardData` / `useCollectionCardData` / a custom one for /promos), the strip computation (zone-aware add controls, in-collection select shift-range, ambiguous-variant routing), click handlers, drag IDs, format presets. What never stays at the surface: chrome assembly, thumbnail wiring, default table actions, default toolbar layout, the detail overlay and what a card click opens.

Worked examples: `apps/web/src/components/card-browser.tsx` (catalog), `apps/web/src/components/collection/collection-grid.tsx` (most complex, with browse/select/add modes), `apps/web/src/components/deck/deck-card-browser.tsx` (deck zones), `apps/web/src/routes/_app/collections_.share.$token.lazy.tsx` (simplest), `apps/web/src/routes/_app/promos_.$language.lazy.tsx` (custom non-virtualized grid).
